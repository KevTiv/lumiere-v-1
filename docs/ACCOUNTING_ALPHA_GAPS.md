## Strict limits

- **Bank settlement:** exact full bank amount, one partner, posted customer invoices or supplier bills, and one compatible AR/AP clearing account in the same organization/company and company base currency. All outstanding AR/AP items of every selected document must be included. Foreign currency, refunds/netting, partial allocations, residual write-offs and automatic matching are outside this desk's supported path. Suggestions still require review.
- **Closed bank approvals:** an open payment approval supports approval followed by explicit settlement completion. If its task is rejected or invalidated, or its workflow instance is cancelled, the unposted draft payment and bank line remain pinned to the original settlement. Retrying reuses that task; it does not reopen it or create a replacement. There is currently no supported resubmit or abandon operation, and generic payment cancellation or bank-line unlinking cannot release it. Rejection itself creates no posted payment or invoice allocation. This is a recovery gap even before financial posting; a dedicated draft-abandon/resubmission lifecycle must be implemented before users can rely on recovering those outcomes. The task model has no separate expired status: an expired approver role/delegation grant leaves an open task pending and requires valid authorization before a decision can succeed. Republishing workflow policy or editing persisted records is not a supported recovery procedure.
- **Reversal:** bank-owned payments cannot be cancelled, unregistered, reallocated or reversed through generic payment operations. Ordinary bank-line editing cannot manufacture settlement provenance. A dedicated coordinated bank-settlement reversal workflow remains to be implemented; there is no unlink shortcut.
- **Money:** posting/reconciliation normalize supported values through integer minor units within the existing pilot monetary envelope. This addresses binary subtraction dust and a valid last-cent settlement; it is not a migration of all persisted accounting money away from `f64`.
- **Email:** queue confirmation, provider acceptance and recipient delivery are distinct outcomes. A consumed dispatch claim with an uncertain provider response/receipt stays unknown and has no automatic resend/reset path. Attachments reuse the managed invoice renderer and are limited to 8 MiB. The legacy batch endpoint is disabled; existing legacy queue entries need deliberate per-message review rather than automatic draining. There is no general attachment composer, placeholder expansion engine, delivery webhook certification or issuance-time PDF archival in this work.
- **Email volume:** per-message dispatch lookup is bounded to its ID. Queue-token deduplication still scans the organization's mailbox, and shared PDF/browser readback paths acquire broader resource lists. Indexing and narrower reads remain follow-up work for large histories.
- **Bill intake:** manual managed uploads and review only; PDF, PNG, JPEG or WebP up to 20 MiB. There is no OCR, automatic bill extraction or accounting posting from uploaded bytes. Unknown-link recovery is scoped to its original actor/company/bill; a full browser reload does not provide a durable client attempt journal.
- **Import review:** displayed totals are a source review aid. They do not establish successful import, ledger control-total agreement or accountant acceptance.
- **Period close:** a generated report step means a report exists for the selected range. It does not independently certify current ledger totals, tax correctness, report freshness or statutory filing. Actual close remains an explicit server-validated operation; source failures never count as completed checks.
- **Loading:** mounted HTTP reads are bounded. The opt-in legacy direct subscription layer still accumulates the union of visited resources for the browser session. Removing that union and fully decomposing the large accounting controller remain follow-up work.
- **Rwanda:** real RRA/VSDC exchange is out of scope pending official specifications and an approved integration/certification plan. These changes do not turn the existing adapter stub into a statutory integration. Country-pack acceptance, legal/tax review and the separate statutory gate in the [Rwanda rehearsal](RWANDA_ACCOUNTING_ALPHA_REHEARSAL.md) remain required.

## Contracts: safe local candidate sequence

The application currently consumes `lumiere-contracts` **0.3.120**. Clean corrected-source generation and the local `0.3.121-alpha.0` candidate above are validated; they are not published. The new denied `erp.claim_reviewed_mail_delivery` operation and expanded projections still require a coherent reviewed release/pin before release. Checks against the existing application pin do not replace validation of that later pin.

This is a release-consistency gate, not a claim that the API cannot function before an external SDK release. The dedicated mail route uses the application-local descriptor in `crates/stdb-client/src/generated_reducer_contract.rs` as its runtime authority. Regenerating that descriptor from the new module enables the private API operation for local validation without first publishing an external SDK package. The canonical external pin still remains 0.3.120 until deliberately updated, and that drift must be resolved for release.

1. Generate the module/schema, Rust and TypeScript bindings, presentation schemas, canonical IR and capability artifact from the frozen backend inputs, using the isolated local module/WASM. Follow the generation order in [the release workflow](../.github/workflows/release-contracts.yml). Do not mix new IR with copied old pinned bindings.
2. Compare regenerated operations against the exact pinned 0.3.120 IR and authored history. Review additions, shape/exposure changes, drops and renames. The new reviewed-mail claim must remain denied to generic operations; acceptance receipt authority must remain service-bound.
3. Record one reviewed history revision using the **added-operation-capable append logic** in the release workflow's `Record operation-history revision` step. Preserve retired IDs and the revision chain. Bind the revision to `v0.3.120` and its exact IR digest, `sha256:aa4c2a9d049b36e51aab0f30e5848e17e12cee9330e222f4402da430181e5d3b`.

   `verify-operation-history.py --advance-history-from-release` requires an unchanged active operation-ID set and cannot handle this new operation. `--write-history` rebuilds the baseline and would discard the review chain. Neither is a shortcut for the required append.

4. Commit reviewed authored/generated contract inputs, then regenerate from that clean commit. Generation records dirtiness for `spacetimedb`, `crates/presentation-core`, `lumiere-codegen` and the canonical resource registry. Do not suppress `source_dirty` with an environment override. Require no unexpected changes in those inputs on the second pass.
5. Verify the clean staging artifacts without publishing:

   ```bash
   python3 scripts/verify-contract-ir.py .contracts-staging/ir/lumiere-contract-ir-v2.json --require-clean
   python3 scripts/verify-operation-history.py
   python3 scripts/verify-agent-capability-artifact.py .contracts-staging/ir/agent-capability-registry-v1.json
   ```

6. Prepare one local candidate with a fresh directory and a local contracts checkout. The example uses a prerelease version to distinguish the unshipped candidate; record the selected version and candidate commit in the verification table.

   ```bash
   LUMIERE_CONTRACTS_PREPARE_DIR=/tmp/lumiere-accounting-alpha-next-review \
   LUMIERE_CONTRACTS_REPO=/workspace/lumiere-contracts \
     make publish-contracts-prepared VERSION=0.3.121-alpha.0
   ```

   The prepare directory **must be nonempty as an environment value and absent on disk before starting**. In this mode the publisher constructs and commits the local candidate, checks Rust with all features, builds/typechecks TypeScript, and exits before push/tag. Omitting `LUMIERE_CONTRACTS_PREPARE_DIR` enables the publisher's remote publication path. Do not invoke that path for local validation.

7. In the prepared clone, run the contracts-owned generator drift check (`python3 scripts/generate-from-ir.py --check`) and the existing resource-codec/capability tests against the built outputs. Package a review-only Rust bundle and npm tarball if needed to verify the application in a disposable checkout; keep candidate files separate from the current vendored release until the candidate/pin change is reviewed.
8. Verify durable migration promotion/catalog consistency before any release. Source and contract generation alone cannot release a pending durable migration.
9. A later release must pin one reviewed contracts revision/version consistently across the Rust bundle/checksum, npm tarball, Cargo and pnpm lockfiles, frontend package manifests, presentation contract pin, generated metadata and `release-compatibility-manifest.json`. Re-run release-manifest/source-drift checks and the application checks against that coherent set. A prepared local candidate is not a published release.

This document does not authorize publishing a contracts tag, pushing the candidate, modifying an external tenant or deploying services. The draft backend branch is intentionally excluded from automatic immutable contracts publication.

## Configuration and remaining release gate

Reviewed email requires provider credentials, the managed PDF renderer when attachments are selected, and a dedicated `LUMIERE_REVIEWED_MAIL_STDB_TOKEN` with an active per-organization `reviewed_mail_dispatcher` binding. The API validates that authority before claiming/sending. Follow the [email runbook](ACCOUNTING_EMAIL_DISPATCH.md); this work does not create or rotate production secrets or bindings.

Role changes in the Rwanda setup script are explicit persona capabilities, not edits to a live tenant. Document intake additionally requires document read/create permissions. Required fields intentionally redacted by a tenant policy must remain unavailable; do not bypass field policy to make a screen green.

Release still requires the clean regenerated contracts/pin and configuration above, a consistent deployed web/API/module version, passing end-to-end operational evidence, and the named user's/accountant's acceptance. Onboarding, production recovery drills and statutory certification retain their own gates.
