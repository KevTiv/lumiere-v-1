## 1. Why this runs first

The application-contract IR is greenfield and will churn its generated output heavily. Every iteration of that churn lands in application PRs as thousands of regenerated files unless the distribution boundary exists first.

Original generated footprint before the first extraction:

| Tree | Files | Generated by |
|---|---:|---|
| `api-server/src/stdb_sdk_bindings/` | 3,021 | `spacetime generate --lang rust` |
| `frontend/packages/stdb/src/generated/` | 1,721 | `spacetime generate --lang typescript` |
| `crates/stdb-auth/assets/` (generated subset) | 6 | `lumiere-codegen` |

Establishing the release boundary now also forces the versioning question to be answered before the IR shape is designed around it, rather than retrofitted.

## 2. Decisions

| Decision | Choice |
|---|---|
| Repository | Create `KevTiv/lumiere-contracts` (private) now |
| Rust distribution | Tag-pinned private git dependency from the start — no cargo registry |
| TypeScript distribution | Tag-pinned `packages/contracts` exists; package-registry publishing remains pending |
| Completed first scope | Generated Rust/TS STDB bindings + generated manifests extracted |
| Current scope | Canonical IR handoff and downstream-emitter boundary |
| Later scope | Drizzle/offline artifacts and framework-neutral generated clients/hooks |

### 2.1 Refined generator boundary

The original plan treated all generator implementation as a
`lumiere-v-1` responsibility. The refined boundary is narrower:

- `lumiere-v-1` parses Rust/STDB source and authored application metadata,
  normalizes them, and publishes canonical versioned IR;
- `lumiere-contracts` consumes a pinned IR digest and owns target-specific
  TypeScript/Rust emission, domain directories, mechanical React Query hooks,
  barrels, export maps, compatibility checks, and package publishing;
- handwritten form mappers, parameter finalizers, authorization, and business
  rules stay in `lumiere-v-1`.

No contracts build may clone or inspect mutable application source. This avoids
two repositories independently deciding what Rust/STDB means.

Current implementation emits
`.contracts-staging/ir/lumiere-contract-ir-v1.json` and a SHA-256 sidecar.
`make check-contract-ir` validates the envelope, ordering, cross-links,
semantic hash, and artifact checksum.

Generated PG DDL stays local for now: `api-server/src/cold_tier/migrate.rs:20-29` consumes it via `include_str!` as a build intermediate, not as a released contract artifact. It qualifies as *Investigate* under the scope rule and does not need to move to unblock the IR work.

## 3. The circular-dependency constraint

The first scope moves both an input and an output of `lumiere-codegen`:

```text
api-server/src/stdb_sdk_bindings/   → INPUT to stdb_bindings_parse.rs
crates/stdb-auth/assets/*.json      → OUTPUT of lumiere-codegen
                                    → also include_str! INPUT to stdb-auth
```

Moving both naively means `lumiere-v-1` cannot build its own generator input, and `stdb-auth` cannot compile. Cargo git dependencies resolve into `~/.cargo/git/checkouts/<hash>/`, which is not a stable path for a file-scanning parser.

**Transitional rule:** authoritative extraction reads a gitignored staging
checkout; runtime reads published packages. While emitters are being ported,
the staging area still holds both inputs and generated targets. The end state
removes this circularity: extraction publishes IR, and the contracts repository
generates every target solely from that pinned IR.

```text
lumiere-v-1 module source
        ↓ spacetime generate --lang rust
.contracts-staging/ir/lumiere-contract-ir-v1.json
        ↓ publish immutable artifact + checksum
lumiere-contracts pins digest and runs target-owned emitters
        ↓ validate + compatibility check
        ↓ tag vX.Y.Z
lumiere-v-1 bumps the pinned tag
        ↓
stdb-auth / api-server compile against the crate
```

## 4. Versioning

Three independent axes, per [private-generated-contracts-repo.md §4.3](./private-generated-contracts-repo.md). Keeping them separate is what makes a compatibility break mechanically detectable rather than a judgment call.

| Axis | Location | Bumped when |
|---|---|---|
| contract package semver | `CONTRACT_VERSION` + git tag | any released change across bindings/manifests |
| schema version | `LumiereSchemaManifest.version` (currently `1`) | the serialized IR *shape* changes |
| sync protocol version | `manifests/compatibility.json` | wire protocol compatibility changes |

`manifests/compatibility.json` is generated from day one, even while it only carries the schema axis. Adding it later means retrofitting compatibility history that was never recorded.

Release rules:

- one git tag identifies one coherent release across bindings, manifests, and (later) TS;
- `lumiere-v-1` pins a tag or immutable SHA, never a branch;
- a schema-version bump without a contract-version bump is a CI failure, and vice versa where the shape actually changed.

## 6. IR defects this workstream should close

Extraction is the right moment to fix these, because after extraction the manifest *is* the published contract and its fields become load-bearing.

1. **U64 JSON representation is lossy.** `codec_emit.rs:154-188` declares `api_json: "string"` for `U64`; the runtime returns a JSON number (`api-server/src/cold_tier/pg_codec.rs:112-121`). Ids above 2^53 silently lose precision at the JS boundary — the exact failure [sliding-window-cold-tier.md §3.3](./sliding-window-cold-tier.md) forbids. `pg_bind` / `pg_from` / `api_json` currently have zero consumers.
2. **The type→PG mapping is duplicated three times** with no consistency assertion: `pg_ddl_emit.rs:152-173`, `codec_emit.rs:117-132`, and string-matched again in `pg_codec.rs:111-166`. Divergence regenerates consistently-wrong artifacts that `check-codegen` cannot see.
3. **Parser silent-skip paths.** A missing type file, an unparseable `*_table.rs`, or a malformed archive candidate warns and continues with exit 0 (`stdb_bindings_parse.rs:52-58,302-307`; `cold_tier/mod.rs:99-102`). Once the manifest is a released artifact, a silently-dropped table ships.
4. **Unquoted DDL identifiers.** `pg_ddl_emit.rs:86-104,127-139` interpolate raw; `dashboard_widget.limit` and `form_config_field.order` would emit invalid SQL if either became a candidate.

## 7. Known collision with the capability IR

[agent-ir-codegen-extension-plan.md](./agent-ir-codegen-extension-plan.md) requires generating result-policy **enforcement adapters** and a tool registry into the contracts package — i.e. runtime behavior. [private-generated-contracts-repo.md §2](./private-generated-contracts-repo.md) marks "generated SDK runtime code with transport behavior" as *Investigate* and forbids moving authorization/policy code.

Decision: `lumiere-contracts` may emit declarative capability descriptors,
operation schemas, tool-registry data, and pure serialization/validation code.
It must not emit or own authorization decisions, approval routing, tenant
scope enforcement, result-policy enforcement, tool execution, or transport
orchestration. Those runtime adapters remain in `ai-gateway` and consume the
versioned descriptors. This keeps enforcement reviewable beside the trusted
runtime while allowing inert capability contracts to share the IR release.

## 8. Exit gate

1. `lumiere-v-1` contains no generated Rust STDB bindings and no generated manifests;
2. all generated-asset access goes through the pinned contracts crate;
3. authoritative extraction runs from source into canonical IR; downstream
   generation runs only from the pinned immutable IR artifact;
4. a schema change produces a contracts PR + tag + a one-line dependency bump in `lumiere-v-1`;
5. `make check-codegen` fails when the pinned tag drifts from local generation;
6. the three version axes are distinct and recorded in `compatibility.json`.
