# Production v0.1 Readiness Plan

## Outcome

Ship a deliberately scoped production v0.1 for design-partner pilots. The release
proves tenant onboarding, lead-to-cash, procure-to-pay, accounting close/import,
and governed AI insights/action drafts. It does not claim production depth for
every module currently visible in the application.

Current release posture is **no-go**. The ERP wedge has a credible foundation,
but build gates, AI enforcement, browser coverage, recovery, and operations must
be completed before real pilot data is accepted.

## Release Scope

### Included

- Authentication, organization bootstrap, company setup, and permission setup.
- Lead-to-cash: lead/customer, quotation/order, delivery, invoice, payment, and
  accounting trace.
- Procure-to-pay: supplier, purchase order, receipt, bill, three-way match,
  payment, and accounting trace.
- Accounting import, validation, period close, correction, and owner reports.
- One green AI report/insight through an immutable promoted skill version.
- Governed AI action drafts with preview, approval, separation of duties, audit,
  and deterministic execution allowlists.
- Production deployment, monitoring, backup/restore, incident, and rollback
  procedures required to operate the included scope.

### Excluded unless separately proven

- Production certification of every visible CRM, HR, projects, subscriptions,
  helpdesk, fleet, proposals, and workflow feature.
- Autonomous AI mutation.
- Arbitrary model-, browser-, or user-provided SQL.
- Unreviewed global skills, generated executable code, or unrestricted network
  and filesystem access.
- Point-in-time recovery claims that the chosen SpacetimeDB hosting arrangement
  cannot demonstrate.

## Evidence Baseline

The repository already contains substantial ERP reducers, scoped BFF routes,
permission enforcement, AI version/release/action-draft foundations, unit tests,
and 149 discoverable Playwright tests. The release baseline is nevertheless red:

- Frontend typecheck fails in the proposals query hook.
- Reducer parameter coverage is 173/261 (66.3%) against a 100% gate.
- i18n checks report missing UI and web application keys.
- ESLint 9 has no runnable flat configuration.
- The full E2E workflow does not start Qdrant or the AI gateway, and AI tests can
  skip when the gateway is absent.
- Pull-request E2E path filters omit ordinary frontend and AI gateway changes.
- AI fixture passes can be recorded from caller-provided output instead of an
  executed harness run.
- Only a small subset of skills is fenced from the legacy orchestrator.
- Production Compose, readiness, metrics, and documented recovery are incomplete.

## Definition of Done

Production v0.1 is releasable only when all conditions below are true:

1. A fresh checkout passes formatting, lint, typecheck, code generation, mapping,
   i18n, unit, Rust, build, and P0 browser gates in CI.
2. A fresh empty tenant completes onboarding, lead-to-cash, procure-to-pay,
   import, accounting close, and correction without seed-only shortcuts.
3. AI tests run hermetically and cannot skip in a release job.
4. Every production AI run references an immutable active skill version and
   records its resolved policy, scope, resources, privacy transformation, actor,
   inputs/outputs fingerprints, and artifacts.
5. Skill fixture results are produced by server-side execution; the browser
   cannot assert its own passing result.
6. AI cannot execute mutations directly. Elevated drafts require an eligible
   different approver and a declared correction strategy.
7. Production readiness fails when required dependencies are unreachable.
8. Dashboards and alerts cover service availability, latency, errors, background
   work, workflow failures, AI denials/cost, and dependency health.
9. A backup can be restored in a timed drill and the demonstrated RPO/RTO is
   documented in the pilot agreement.
10. A release candidate survives a staging soak and a controlled pilot rollout
    with an exercised application and data rollback procedure.

## Delivery Sequence

### Phase 0 - Freeze the v0.1 Contract

Goal: prevent broad module work from obscuring the release-critical wedge.

- Convert the included scope above into a signed release checklist.
- Mark unproven modules as preview, hide them from pilot navigation, or explicitly
  exclude them from support commitments.
- Assign component owners for ERP workflows, AI harness, frontend, platform,
  security, and release operations.
- Record the supported deployment topology, model provider, data region,
  retention policy, expected pilot volume, and availability objective.
- Reconcile `V1_ROADMAP.md`, `MVP_WORKFLOW_CONTRACT.md`, and this plan so the
  repository has one current release truth.

Exit gate: scope, operators, pilot assumptions, and go/no-go authority are named.

### Phase 1 - Recover the Release Baseline

Goal: make every deterministic repository gate green before feature hardening.

- Fix the typed reducer name mismatch in the proposals hook.
- Map or intentionally exclude every generated reducer parameter type; keep the
  CI minimum at 100% for in-scope generated contracts.
- Add all missing translation keys and make duplicate/missing-key checks blocking.
- Add an ESLint 9 flat configuration and resolve production-code findings.
- Add `pnpm build` and lint to frontend CI.
- Run full relevant tests for `api-server` and `ai-gateway`, not name-filtered
  health/allowlist tests only.
- Add `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and the
  release-relevant workspace test set. Resolve warnings instead of suppressing
  correctness, suspicious, performance, or async findings broadly.
- Keep code generation reproducible and assert a clean tracked worktree after it.
- Ensure CI builders have enough disk/cache policy for bundled native crates
  during the transition away from DuckDB.

Exit gate: one clean CI run from a fresh checkout, with no skipped required job.

### Phase 2 - Make Golden Workflows Release-Proving

Goal: prove business outcomes rather than only isolated pages or seeded states.

- Add an empty-tenant bootstrap fixture that uses production onboarding paths.
- Execute lead-to-cash and procure-to-pay from that tenant, asserting documents,
  stock effects, ledger postings, residual balances, and audit history.
- Add import preview/commit/rollback and accounting close/correction to the same
  release suite.
- Assert organization and company isolation at every workflow boundary.
- Add negative permission, duplicate submission, idempotency, stale state,
  retry, and partial-failure cases.
- Make P0 run on every relevant pull request and the full suite run on main and
  release candidates. Include `frontend/web/**`, frontend packages,
  `ai-gateway/**`, deployment configuration, and shared Rust crates in triggers.
- Publish traces, screenshots, service logs, and database logs on failure.

Exit gate: the scoped ERP contract passes repeatedly from an empty database.

### Phase 3 - Close the AI Harness

Goal: establish one production execution authority with default-deny behavior.

- Complete the separate DuckDB removal plan.
- Implement the detailed execution work in
  `ai-unified-execution-capabilities-subagent-plan.md`: approved scoped SQL and
  tenant/desktop file brokers remain supported, while raw shared-database SQL
  and process filesystem access remain unavailable.
- Fence or disable legacy `/v1/skills/run` for every production skill.
- Require an active immutable release for all green, amber, and red paths.
- Resolve permissions, organization/company scope, resources, privacy policy,
  budgets, and output types on the server; trust none of these from the browser
  or model.
- Record a policy snapshot for every run and preserve historical version IDs.
- Replace caller-recorded fixture outcomes with an executor-owned test-run
  command that binds version, fixture, actual output, logs, and fingerprints.
- Require fixture execution and approval before promotion; test rollback while
  retaining historical run metadata.
- Keep green skills read-only. Keep amber/red behavior limited to typed drafts.
- Test cross-company access, unknown resources, unscoped/raw SQL, oversized
  results, direct reducers, secret access, path/grant escape, unreviewed network
  attempts, approval bypass, and self-approval; deny and audit every case. Also
  prove approved tenant-scoped SQL and file grants remain inside their declared
  organization/company/device boundaries.

Exit gate: promote -> execute -> inspect audit -> roll back succeeds in a
hermetic E2E environment, and all escape tests fail closed.

### Phase 4 - Production Deployment and Operations

Goal: make deployment failure visible and recovery demonstrable.

- Correct and validate all Compose/runtime wiring, including the API server URL
  required by AI report composition.
- Add startup validation for secrets, URLs, provider selection, token separation,
  and production-only unsafe defaults.
- Add container healthchecks and dependency-aware readiness for SpacetimeDB,
  Qdrant where retained, model/embedding services where required, and API/AI
  dependencies. Network errors must fail readiness.
- Add explicit HTTP connect/request timeouts, bounded retries with jitter, and
  circuit behavior for external dependencies.
- Terminate TLS at a documented ingress, restrict service exposure, narrow CORS,
  rotate secrets, and verify rate/request-size limits.
- Replace global request counters with route/status latency and error metrics;
  add workflow queue, import, document, AI run/denial/token/cost, and dependency
  metrics with actionable alerts.
- Select and document the production SpacetimeDB backup mechanism. Build any
  required full export/restore pipeline, automate encrypted retention, and run a
  restore drill. Do not describe partial tenant JSON as full disaster recovery.
- Document deploy, migration, rollback, incident, data correction, and provider
  outage procedures with named owners.

Exit gate: production-like staging passes failure injection and timed recovery.

### Phase 5 - UX, Accessibility, and Performance Gate

Goal: ensure operators can safely complete the supported workflows.

- Associate every AI and ERP form control with a programmatic label and error.
- Make important AI harness tabs and selected records deep-linkable.
- Add automated accessibility checks to P0 pages and keyboard-test approvals,
  close, imports, and action drafts.
- Split only the largest client modules where measurement shows costly initial
  bundles or rerenders; preserve workflow cohesion.
- Load-test the agreed pilot concurrency and data volumes for reports, imports,
  workflow workers, and AI runs.
- Verify audit views, error recovery, empty/loading states, destructive-action
  confirmation, and user-visible correlation IDs.

Exit gate: accessibility, performance, and operator acceptance thresholds pass.

### Phase 6 - Release Candidate and Pilot Rollout

Goal: release with bounded blast radius and observable acceptance criteria.

- Build immutable images and publish a software bill of materials and release
  manifest containing source revision, schema/module version, skill versions,
  configuration version, and migration state.
- Deploy to staging from the same artifacts intended for production.
- Run the complete release suite and a staging soak with representative scheduled
  jobs and provider calls.
- Create the production backup/recovery point, deploy one pilot tenant, execute
  smoke workflows, and monitor before adding another tenant.
- Define stop conditions for ledger mismatch, cross-tenant exposure, failed
  restore, elevated AI policy bypass, unbounded error rate, or missing audit.
- Hold a written go/no-go review and attach CI, E2E, security, restore, load, and
  accessibility evidence to the release record.

Exit gate: the release authority signs v0.1 only with every P0 item evidenced.

## Required CI Matrix

| Gate | Pull request | Main | Release candidate |
| --- | --- | --- | --- |
| Format, lint, typecheck, mapper, i18n | Required | Required | Required |
| Rust check, Clippy, unit/integration tests | Required | Required | Required |
| Frontend unit tests and production build | Required | Required | Required |
| P0 browser workflows | Relevant changes | Required | Required |
| Full browser workflows | Optional | Required | Required |

| Security/escape tests | Relevant changes | Required | Required |
| Container/config smoke | Relevant changes | Required | Required |
| Restore and load evidence | Scheduled | Scheduled | Required |

Branch protection must require the applicable jobs; workflow files existing in
the repository is not sufficient evidence.

## Go/No-Go Checklist

- [ ] Release scope and exclusions are signed.
- [ ] All required CI jobs are green and branch-protected.
- [ ] Empty-tenant ERP golden paths pass.
- [ ] AI release, fixture, policy snapshot, approval, and rollback gates pass.
- [ ] No arbitrary SQL or direct AI mutation path remains enabled.
- [ ] Production dependency readiness and alerts pass failure injection.
- [ ] Backup restoration meets the documented pilot RPO/RTO.
- [ ] TLS, secrets, CORS, rate limits, and provider/data policies are approved.
- [ ] Accessibility and pilot-volume load checks pass.
- [ ] Staging soak and controlled production smoke pass.
- [ ] Release and rollback authority explicitly approve the deployment.
